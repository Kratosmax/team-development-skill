# 派工记录与模型核验

Leader 必须在实际工作中落实分级和选型，并让用户在对话中看见。完整要求见 [SKILL.md](../SKILL.md)，具体模型发现与路线见 [模型路由](model-routing.md)。这份规则约束维护 agent 的操作，不修改宿主 GUI，不保证底层提供商实际执行的内部模型身份。

## 1. 启动前的批量派工表

先读取可用模型，再按具体任务列出精简记录。以下全部是格式示例，不是已启动任务、真实 ID 或本轮选型证据：

| 任务/职责 | 级别与理由 | 请求 provider / model | 推理强度 | 上下文 | 状态 |
| --- | --- | --- | --- | --- | --- |
| T1 / 展示组件 | 初级：边界清楚、局部改动、易验证 | 当前发现的提供商 / GLM Flash 精确 ID | 该模型支持值或不支持 | 全新独立 | 计划，尚未启动 |
| T2 / 数据查询 | 中级：需跨文件理解、风险可控 | 当前发现的提供商 / GLM 正式版精确 ID | 该模型支持值或不支持 | 全新独立 | 计划，尚未启动 |
| T3 / 状态一致性 | 高级：涉及并发与关键状态 | 当前发现的提供商 / GPT Sol 精确 ID | 该模型支持值或不支持 | 全新独立 | 计划，尚未启动 |

真实使用时必须填入当前工具允许的精确 ID，不能把上面占位文字传给工具。简短任务可以合并“上下文”和“状态”列。只为当前就绪任务安排实际启动；依赖尚未完成的审查者可标为排队，不提前声称运行。展示是告知，无需用户确认后才派工；独立工作仍同轮批量启动。

## 2. 调用必须与记录一致

Leader 执行前核对任务、provider、model、reasoning_effort 和上下文语义。接口支持 provider/model 且适合任务时，两者均显式设置；推理参数不受支持时省略并注明不支持。角色级别是任务决策，不是随意换一个角色名或推理强度就完成模型升级。

当前 DSH 中，subagent 适合新上下文及显式选型；spawn_teammate / subagent_fork 当前没有选型参数。对后两者不能伪造参数；需要指定模型时优先适合任务的 subagent。必须使用持久团队能力等其他要求时，说明具体取舍与默认路线，仍保留任务分级及型号证据。换环境后先核对新工具签名，不把该例子写死为通用能力结论。

不要为制造“初中高级齐全”的表格而额外启动无用代理。对每个真实任务选适合的档位；全部是简单任务时允许全部用初级，有理由全部高级也应公开理由。

## 3. 启动后的核验与状态

回执返回后及时把真实代理 ID/成员目标关联到任务，可批量更新，不需逐个阻断其他启动。开始前和开始后的记录要对应：

| 字段 | 记录要求 | 不能据此推断的内容 |
| --- | --- | --- |
| 请求参数 | 来自实际工具调用，含 provider/model/强度；无选型参数写平台默认 | 不能单凭提交参数保证底层执行型号 |
| 启动回执 | 返回的代理 ID 或成员目标，创建失败则记录失败及原因 | 有 ID 不等于模型已核验或任务已完成 |
| 执行型号证据 | 来自该代理关联的回执、成员详情、路由元数据或执行记录，记来源与观察时间 | 名称、角色、结果风格、子代理自报身份均不是独立证据 |
| 生命周期 | 排队、已启动、已完成、失败、已替换、已取消等实际状态 | 不将 inactive、ready 或“取消已请求”直接当作完成 |

证据只证明工具报告的路线；如提供商没有暴露底层执行型号，就保留这一限制，不能宣称已鉴定其内部模型。可先报告“已请求某 provider/model；回执仅返回 ID，执行型号未核实”，有新证据再更新。能力查询不覆盖某种子代理类型时不要从列表缺失推断任务未启动；按该类型正式结果与记录回收。没有可用查询接口时不反复调用或读私有运行时文件搜型号。

启动失败要保留失败条目，按真实原因判断重试或更换路线，不能把失败请求列为已运行代理。正常元数据核对是只读检查，不额外生成“请自报模型”的子任务。

## 4. 升级、替换及最终报告

升级新代理保留原任务 ID，再分配新的代理 ID 并标注替换关系、原因和新模型路线；先控制旧代理写入，按全新独立上下文交接规则执行。原条目保留为已替换或失败，不覆盖历史后假装一开始就在用高级模型。

最终回复保留用户关心的结果与验证，同时给出精简派工摘要：

| 任务 | 代理 ID/目标 | 级别 | 已请求模型 | 执行型号/证据 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 示例任务（非真实记录） | 工具返回 ID | 中级及简短理由 | 实际调用的 provider/model | 未核实：回执无型号字段 | 以实际结果填写 |

有多次增派、失败和替换时覆盖全部本轮代理，可用同一任务下多行或关联 ID 表达，不必重复整个调用日志。普通选型未发生升级也要可见，不能仅在降级时报告。任务多时先按功能概括，在项目内已有记录中保留完整明细并链接；对话摘要仍须包含各代理的任务、级别与型号核验状态。

## 5. 自检场景

- **可选模型而漏传参数**：不能称已按级别设置模型；发现后核对任务是否启动，控制旧写入并用真实参数修正，记录替换关系，不隐瞒旧请求。
- **只返回代理 ID**：记录请求已提交及执行型号未核实；不以代理自报补齐证据。
- **不可选模型但返回型号元数据**：明确无法选型，同时显示工具报告的型号及任务级别；不强行写未知。
- **界面没有模型卡片**：仍在对话展示派工表和结果摘要；不要声称已改 GUI。需要原生卡片才涉及客户端开发，应作为明确的独立需求处理。
- **发现平台实际模型与请求不同**：展示两者与证据，核实提供商路由/降级事实；未查实前不归因，不继续虚报已使用首选模型。
- **任务升级或代理取消**：新旧 ID 可关联；确认旧范围不再写入后交接，取消请求本身不能当作已停止。
- **多个独立任务**：先批量记录并启动，后批量绑定 ID；模型记录不能变成逐项等待、逐项确认的串行门禁。
