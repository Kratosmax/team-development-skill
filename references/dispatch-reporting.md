# 派工记录、实现归属与模型核验

Leader 必须在实际工作中落实分级和选型，并让用户在对话中看见。完整要求见 [SKILL.md](../SKILL.md)，具体模型发现与路线见 [模型路由](model-routing.md)。这份规则约束维护 agent 的操作，不修改宿主 GUI，不保证底层提供商实际执行的内部模型身份。

## 1. 启动前的批量派工表

先读取可用模型，并按 [成员生命周期](agent-lifecycle.md) 检查兼容成员与预算，再按具体任务列出精简记录。以下全部是格式示例，不是已启动任务、真实 ID 或本轮选型证据：

| 任务/类型与职责 | 预期产物、负责人/写入范围 | 级别与理由 | 请求 provider / model | 推理强度 | 上下文 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| T1 / UI 实现：展示组件 | 可运行组件；子代理 A / 展示组件文件 | 初级：边界清楚、局部改动、易验证 | 当前发现的提供商 / GLM Flash 精确 ID | 该模型支持值或不支持 | 全新独立 | 计划，尚未启动 |
| T2 / 代码实现：数据查询 | 查询代码与检查证据；子代理 B / 查询模块 | 中级：需跨文件理解、风险可控 | 当前发现的提供商 / GLM 正式版精确 ID | 该模型支持值或不支持 | 全新独立 | 计划，尚未启动 |
| T3 / 代码实现：状态一致性 | 状态逻辑与验证；子代理 C / 状态模块 | 高级：涉及并发与关键状态 | 当前发现的提供商 / GPT Sol 精确 ID | 该模型支持值或不支持 | 全新独立 | 计划，尚未启动 |

真实使用时必须填入当前工具允许的精确 ID、具体负责人和文件/模块范围，不能把上面占位文字传给工具。简短任务可以合并“上下文”和“状态”列。只为当前就绪任务安排实际启动；依赖尚未完成的审查者可标为排队，不提前声称运行。展示是告知，无需用户确认后才派工；独立工作仍同轮批量启动。

表格与委派正文共同构成真实交付合同：明确设计方案、代码/UI 实现、审查或集成类型，补齐验收条件、可用工具/环境及限制。开发任务默认交子代理直接读代码、编辑授权范围并验证，不用“扮演某角色给建议”代替实现派工。独立设计/分析/审查可只交规范、原型或意见，无须代码补丁；UI 实现仍按代码难度分级并结合设计能力选型。

## 2. 调用必须与记录一致

Leader 执行前核对任务、provider、model、reasoning_effort 和上下文语义。新建时接口支持 provider/model 且适合任务，两者均显式设置；续派兼容成员则按生命周期规则引用既有选型证据，不能假装通信接口重新指定了模型；推理参数不受支持时省略并注明不支持。角色级别是任务决策，不是随意换一个角色名或推理强度就完成模型升级。

当前 DSH 中，subagent 适合新上下文及显式选型；spawn_teammate / subagent_fork 当前没有选型参数。对后两者不能伪造参数；新建需要指定模型时优先适合任务的 subagent；已有成员符合本任务且可续派时按生命周期规则复用，不为再次显式选型而重复新建。必须使用持久团队能力等其他要求时，说明具体取舍与默认路线，仍保留任务分级及型号证据。换环境后先核对新工具签名，不把该例子写死为通用能力结论。

不要为制造“初中高级齐全”的表格而额外启动无用代理。对每个真实任务选适合的档位；全部是简单任务时允许全部用初级，有理由全部高级也应公开理由。

## 3. 启动后的核验与状态

回执返回后及时把真实代理 ID/成员目标关联到任务，可批量更新，不需逐个阻断其他启动。派工记录注明新建或复用及理由，续派沿用真实成员 ID，但分配新的任务 ID；按唯一成员 ID 计算人数，不能把同一成员的多次任务当作多名成员。模型级别、上下文与独立性不兼容时不复用。开始前和开始后的记录要对应：

| 字段 | 记录要求 | 不能据此推断的内容 |
| --- | --- | --- |
| 请求参数 | 来自实际工具调用，含 provider/model/强度；无选型参数写平台默认 | 不能单凭提交参数保证底层执行型号 |
| 启动回执 | 返回的代理 ID 或成员目标，创建失败则记录失败及原因 | 有 ID 不等于模型已核验或任务已完成 |
| 执行型号证据 | 来自该代理关联的回执、成员详情、路由元数据或执行记录，记来源与观察时间 | 名称、角色、结果风格、子代理自报身份均不是独立证据 |
| 实现归属与产物 | 记录预期与实际实现者、变更文件或补丁、基线及验证命令/结果；结合任务归属、实际工具执行和可见差异核对 | 子代理“完成”消息、角色名称或 Git 作者字段均不能单独证明实际写入者与实现完成 |
| 生命周期 | 分别记录任务结果、执行状态和成员的待命/复用/退出/正式移除；标注本阶段新增、复用次数及清理限制 | 不将 inactive、ready 或“取消已请求”直接当作完成，不把任务完成或中断当作成员已删除 |

证据只证明工具报告的路线；如提供商没有暴露底层执行型号，就保留这一限制，不能宣称已鉴定其内部模型。可先报告“已请求某 provider/model；回执仅返回 ID，执行型号未核实”，有新证据再更新。能力查询不覆盖某种子代理类型时不要从列表缺失推断任务未启动；按该类型正式结果与记录回收。没有可用查询接口时不反复调用或读私有运行时文件搜型号。

启动失败要保留失败条目，按真实原因判断重试或更换路线，不能把失败请求列为已运行代理。正常元数据核对是只读检查，不额外生成“请自报模型”的子任务。

实现任务回收实际文件差异和检查证据；只有思路、代码块或伪代码时记为方案/未完成实现，交回负责人补齐。隔离工作可交基于明确基线的可审查补丁；平台不能编辑时记录真实限制和后续应用/验证负责人，不宣称项目已修改。方案/审查任务按其约定产物验收。

## 4. 升级、替换及最终报告

升级新代理保留原任务 ID，再分配新的代理 ID 并标注替换关系、原因和新模型路线；先控制旧代理写入，按全新独立上下文交接规则执行。原条目保留为已替换或失败，不覆盖历史后假装一开始就在用高级模型。

审核意见优先回原负责人修复，能力不足按既有规则换高级独立上下文。Leader 的接口粘合、共享入口、冲突处理、简单局部修复和自领任务须公开范围；不得借集成重做核心功能或并发抢写。重大接管记具体原因、旧写入已停止的证据、新归属和实际作者；资源限制下由 Leader 实现标为降级。

最终回复保留用户关心的结果与验证，同时给出精简派工摘要：

| 任务/类型、预期产物 | 代理 ID/目标 | 级别 | 已请求模型 | 执行型号/证据 | 实际实现者、文件/补丁、验证及结果 |
| --- | --- | --- | --- | --- | --- |
| 示例 / 代码实现：查询功能（非真实记录） | 工具返回 ID | 中级及简短理由 | 实际调用的 provider/model | 未核实：回执无型号字段 | 实际作者；具体文件/补丁；检查命令与结果，以证据填写 |

无代码变更的方案/审查任务在结果列写交付文档、原型或意见及“无代码变更”。UI 实现结果记录设计交接、实现差异、实际渲染审美证据和负责人修正后的复验；只串相关依赖，独立功能仍并行。

有多次增派、失败和替换时覆盖全部本轮代理，可用同一任务下多行或关联 ID 表达，不必重复整个调用日志。普通选型未发生升级也要可见，不能仅在降级时报告。阶段收尾附人数摘要（运行、兼容待命、本阶段新增/复用）及实际清理状态；未知数量注明不可观测，不把只覆盖持久成员的查询当作全量代理清单。任务多时先按功能概括，在项目内已有记录中保留完整明细并链接；对话摘要仍须包含各代理的任务、级别与型号核验状态。

## 5. 自检场景

- **可选模型而漏传参数**：不能称已按级别设置模型；发现后核对任务是否启动，控制旧写入并用真实参数修正，记录替换关系，不隐瞒旧请求。
- **只返回代理 ID**：记录请求已提交及执行型号未核实；不以代理自报补齐证据。
- **不可选模型但返回型号元数据**：明确无法选型，同时显示工具报告的型号及任务级别；不强行写未知。
- **界面没有模型卡片**：仍在对话展示派工表和结果摘要；不要声称已改 GUI。需要原生卡片才涉及客户端开发，应作为明确的独立需求处理。
- **发现平台实际模型与请求不同**：展示两者与证据，核实提供商路由/降级事实；未查实前不归因，不继续虚报已使用首选模型。
- **任务升级或代理取消**：新旧 ID 可关联；确认旧范围不再写入后交接，取消请求本身不能当作已停止。
- **开发代理仅提建议**：不得标实现完成；补齐直接编辑与检查合同，原负责人交付真实差异，不能默认为 Leader 代写。
- **Leader 接管核心功能**：先停止旧写入、说明原因并更新归属；按实际作者报告，不能记成子代理实现。
- **仅分析/设计/审查**：按约定方案或意见验收，不强行改项目或伪造补丁。
- **多个独立任务**：先批量记录并启动，后批量绑定 ID；模型记录不能变成逐项等待、逐项确认的串行门禁。
