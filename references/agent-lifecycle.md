# 成员复用与生命周期

目标是用有限成员持续并行交付，避免每个任务、每轮反馈都新建代理。并发、待命和阶段新增预算以 [SKILL.md](../SKILL.md) 为唯一数值来源；[派工记录](dispatch-reporting.md) 记录执行证据与人数。

## 盘点与新建判断

每轮安排工作前，根据当前成员查询、已记录的真实 ID、任务归属和完成回执盘点；新会话不盲用历史 ID。无需为每个工具动作重新列全表，但状态变化后要更新记录。当前查询未覆盖的一次性子代理，按其正式回执追踪，不能把列表缺失当作已销毁。

分别统计正在执行的唯一成员、兼容且明确可续派的待命成员、本阶段累计新建、成功续派次数，以及平台只保留的历史条目。任务数不等于成员数；生命周期未知的必需任务不能当作空闲名额。已完成结果留作历史不等于成员仍在运行；退出 Leader 的调度池也不等于从平台删除。

新建前按顺序判断：

1. 找是否有已结束旧任务、可寻址、模型与能力符合本任务的成员；核查上下文相关性、写入范围已释放和独立性。
2. 符合条件且正式接口支持续派时，优先继续同一成员；同一模块的下一小功能、原作者修复审核指出的问题、未参与实现的审核者检查后续修订，通常适合复用。
3. 所有兼容成员仍忙时，若有独立就绪工作且预算允许可新建并行成员；不必为了等待复用把全部工作串行。工作暂未就绪时不预先堆空闲角色。
4. 升级、失败后的独立重做、模型路线不符、不同领域上下文干扰、审核者参与过该项实现或无法确认旧写入停止时，不强行复用。需要隔离时使用正式新建的独立代理，升级必须保留新代理与旧代理的关联；不能用“忘记之前内容”的提示词、改名或同一对话切模型冒充新上下文。
5. 新建或调整预算需在派工记录写一句理由，例如“无可续派目标”“已有合适成员忙，新增独立模块”“升级需隔离”。达到预算后先调度排队、复用、合并无效分工或由 Leader 承担；确需调整必须说明规模、原因和新的上限。不能每轮重置累计数或把一次失败重命名为新阶段。

复用不改变任务定级要求。已有成员模型满足新任务时，记录继承的模型路线及其证据；通信请求没有模型参数就不伪造选型。较强模型继续相关简单收尾工作时说明取舍；不为节省一次新建而把困难工作交给能力不足的成员。

## 续派操作

确认旧任务已交付或明确终止、结果已回收、旧写入已停止，随后分配新任务 ID，保留成员 ID，更新目标、边界、依赖、验收与模型记录。多个独立成员可同轮续派。

持久团队工具支持时，向查询结果返回的真实目标发送下一任务；inactive 只说明当前没在执行，不说明任务已完成或上下文适合。普通子代理仅在当前正式接口明确支持继续、且目标仍有效时续派。出现目标不可寻址后，记录不可续派，不重复发送、不修改内部会话映射；确认旧任务终态后按预算决定替代。

成员在执行时传递必要纠正属于正常协作；不要把它当作已经闲置，抢派第二项互相重叠的写入任务。停止请求也不是写入已停止的证据。

## 每项结束后的自动处理

- 回收结果、差异、实际验证、待办和成员启动的相关后台工作；必要任务未完成时保留状态，不提前声称整个阶段完成。
- 用完成通知、成员状态和相关工具回执核对执行终止。任务板按实际版本规则完成或释放归属；确认不再写入后释放该范围。结果内容和执行终止分别判断。
- 有明确的下一兼容任务时立即续派；尚无下一任务时只保留预算内且很可能再次使用的成员，保留理由。其余从可调度池退出，不发送会意外唤醒它的无用“待命/结束确认”消息。
- 已运行但不再需要的工作按正式停止/取消接口处理并核对结果。没有停止能力且仍在执行时，明确记录待结束及影响范围；不改派同一写入范围，不虚报运行数为零。
- 平台提供关闭、移除或归档接口时，仅处理本任务有归属依据、无未回收结果且已结束的成员；区分关闭执行、释放资源和删除历史的真实效果，并通过独立查询或回执验证。保留必要审计证据，不触碰用户或其他任务成员。

## 阶段结束

Leader 汇总各成员的任务结果与最终去向，并报告四类计数：运行中、可续派待命、本阶段新建、成功续派次数。新阶段只可重置该阶段新增统计，不能清空未结束任务、继承的待命数或原阶段未解决的停止问题。

本阶段无后续需求时不为未来可能使用而一直保留活跃工作。运行、待命、退出、正式移除和仅保留历史分别标注；不提供全量查询或物理清理能力时说明可观测范围。不要把“结果已回收”简称为“所有代理已删除/内存已释放”。

## 当前 DSH 的能力边界（2026-11-12）

- list_agents 查询当前可寻址的持久团队成员；不据此证明历史普通子代理全量状态。
- send_message 可给有效团队目标继续派工；具体普通子代理是否可恢复要看当前正式接口和回执，不能盲信所有历史 subagentId 都可寻址。
- interrupt_agent 中断指定持久成员的当前执行；不删除成员及历史，不保证后台工作已全部结束。job_kill 只处理返回 job_id 的对应后台任务，不能拿代理 ID 充当 job_id。
- 当前注册接口没有成员 close/remove/delete 或历史卡片清理工具。一次性子代理收到完成通知时可确认其本次执行结束，但不能保证平台的内存、并发配额、持久记录均已释放。
- 没有物理清理接口时，减少新增、复用有效目标、结束无用工作并退出 Leader 调度池是可执行的收尾；历史条目仍可能增加。不能通过删除会话文件、数据库、改平台源码或隐藏卡片冒充 skill 已实现回收。需要平台真正释放成员或归档界面时，这是另一个明确的客户端/运行时维护需求。

这些是当前接口观察，换环境先重新检查，不能把此处当作永久限制。

## 验收场景

| 场景 | 应有行为 |
| --- | --- |
| 同模型、同模块的后续任务 | 已结束且可续派则使用同一成员 ID，新任务仍单独定级 |
| 原作者收到修复意见 | 可复用作者修复；最后仍由未参与实现的成员审核 |
| 升级或失败后独立重做 | 新独立上下文；旧范围先停止写入，新旧 ID 关联 |
| 现有成员忙、还有独立任务 | 预算内并行扩充；超额先排队或说明必要调整 |
| 成员 inactive 但没有交付 | 核实任务结果与终态，不直接抢派或清理 |
| 旧 ID 不可续派 | 记不可寻址并停止重试；确认终态后才决定替代 |
| 中断返回成功但后台仍运行 | 不称全部释放，继续回收或取消对应后台任务 |
| 阶段完成但历史卡片仍在 | 如实报告执行结束、记录保留，不谎称删除 |
